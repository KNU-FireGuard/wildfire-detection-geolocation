# FireGuard AI 아키텍처 결정 기록

[시스템 아키텍처](System_architecture.md) · [API 명세](API_SPEC.md) · [ERD](DATABASE.md)

## ADR 0001 · 관리자와 SMS 수신자

- 상태: 채택, 수신자 목록은 ADR 0017로 대체
- 관리자 계정은 `admins`에 저장하고 로그인은 JWT 사용
- 수신자는 관리자별이 아닌 시스템 공용 목록으로 관리
- 비밀번호는 해시로 저장하고 SMS 인증 정보는 Backend에서 관리

## ADR 0002 · 녹화 영상 저장

- 상태: 현행
- 원본 영상은 `data/videos/`에 저장하고 DB에는 경로와 메타데이터 저장
- Backend가 등록 영상을 HTTP Range 방식으로 제공

## ADR 0003 · 영상 4개 일괄 분석

- 상태: ADR 0004로 대체
- 이전 결정: Test 버튼 하나로 녹화 영상 4개를 동시에 분석

## ADR 0004 · 카메라별 테스트와 실시간 구분

- 상태: 현행
- `cameras.source_type` 값은 `test` 또는 `live`
- `test` 카메라별 버튼은 연결된 영상 하나를 분석
- `live` 카메라는 ITS CCTV 영상 주소 사용

## ADR 0005 · Python 표준 출력으로 영상 전달

- 상태: ADR 0006으로 대체
- 이전 결정: Python 표준 출력의 MJPEG 프레임을 Backend가 프론트에 전달

## ADR 0006 · AI 영상·탐지 결과 전송

- 상태: 현행
- AI는 MJPEG 영상을 `POST /api/test-runs/:id/video`로 전송
- AI는 탐지 JSON을 `POST /api/detections`로 전송
- Backend는 영상을 저장하지 않고 `GET /api/test-runs/:id/stream`으로 중계
- 실행 ID로 영상과 탐지 결과를 연결
- Backend가 실행 ID를 생성해 `run_id`, `camera_id`, 영상 경로와 전송 주소를 AI 프로세스 인자로 전달

## ADR 0007 · Test API 인증

- 상태: 채택
- Frontend가 호출하는 Test 실행·상태·영상 스트림 API는 관리자 JWT로 인증
- AI가 호출하는 영상·탐지 콜백 API는 `AI_CALLBACK_TOKEN`으로 인증

## ADR 0008 · Test 실행 중 SMS 중복 방지

- 상태: ADR 0017로 대체(`smoke`는 발송하지 않음)
- 데모에서는 같은 `run_id`와 탐지 클래스 조합에 SMS를 한 번만 발송
- `fire`와 `smoke`는 각각 별도 알림
- 실시간 CCTV의 연속 탐지 이벤트 구분과 재알림 간격은 실제 탐지 누락·오탐을 확인한 뒤 결정

## ADR 0009 · Test 실행 상태 관리

- 상태: 채택
- 실행 상태와 영상 중계 연결은 Backend 프로세스 메모리에서 관리
- 탐지 이벤트는 `detection_events`에 저장하고 같은 실행·클래스의 후속 탐지는 기존 이벤트를 갱신
- Backend 재시작 시 진행 중 실행과 스트림은 종료되며 상태 조회는 유지되지 않음

## ADR 0010 · ITS CCTV 목록 수동 갱신

- 상태: 수동 갱신은 채택, 예시 모드는 ADR 0011로 대체, 24시간 재호출 제한은 ADR 0014로 대체, HTTPS 주소 제한은 ADR 0015로 대체
- 배경: ITS 월 호출 한도 1000건, 지도 방문마다 제공자 API 조회 시 발표 전 한도 소진 가능
- 선택: Backend 관리자 API에서만 ITS 목록 요청, 최대 6개 HTTPS HLS CCTV를 지역 분산 선택해 로컬 파일에 저장
- 선택: 성공·실패 모두 호출 시도를 기록하고 24시간 재호출 차단, 지도 조회는 캐시만 읽음
- 선택: ITS 응답 후 DB 저장 실패 시 대기 목록을 남기고 제공자 재호출 없이 저장 재개
- 선택: 키 없는 fixture 모드는 예시 좌표만 제공하며 실제 영상으로 표시하지 않음
- 대안: 매 화면 조회 시 ITS 요청, 자동 주기 갱신, 브라우저에 ITS 키 전달
- 결과: 정상 갱신 시 월 최대 약 31회 호출, 장애 시 오래된 목록 유지, 실키 테스트에서 HLS·CORS 확인

## ADR 0011 · ITS 예시 모드 제거

- 상태: 채택, ADR 0010의 fixture 모드 선택을 대체
- 배경: 실제 ITS 조회·HLS 재생목록·AI MJPEG 프레임 전달을 확인
- 선택: 예시 CCTV 목록과 모드 분기를 제거하고 저장된 실제 목록만 반환
- 대안: 예시 모드를 개발 전용으로 유지
- 결과: 키 없이도 저장된 목록을 조회할 수 있지만 최초 목록은 비어 있음

## ADR 0012 · 6개 CCTV 감시 작업자 관리

- 상태: 채택
- 배경: 서버가 켜진 동안 6개 영상을 계속 분석해야 하고 AI 담당자의 실시간 코드가 아직 미완성
- 선택: Backend가 저장된 6개 CCTV와 실행 ID를 AI 작업자 한 개에 표준 입력 JSON으로 전달
- 선택: 카메라별 프레임 상태 신호를 수신하고 작업자 종료·120초 신호 누락 시 재시작
- 선택: AI 파일이 설정되지 않으면 대기 상태를 공개하고 ITS 목록 API는 자동 호출하지 않음
- 대안: 카메라마다 YOLO 프로세스 한 개, 수동 60초 실행
- 결과: AI 모델을 한 번 로드할 수 있고 Backend만으로 실행 관리 검증 가능, 실제 분석은 AI 작업자 연결 후 검증

## ADR 0013 · ITS CCTV 주소 정기 갱신

- 상태: ADR 0014로 대체, ADR 0011의 자동 갱신 없음 선택 대체
- 배경: 실시간 영상 주소가 만료될 수 있고 서버를 계속 실행해야 함, 월 호출 한도는 1000건
- 선택: 서버 시작과 화면 조회는 ITS를 호출하지 않고 서버 실행 후 24시간마다 목록 갱신 시도
- 선택: 호출 시도 기록으로 최소 24시간 간격 유지, 성공 시 감시 작업자에 새 주소 전달
- 대안: 화면 조회 때마다 호출, 수동 갱신만 사용
- 결과: 장시간 실행 시 약 30회/월 요청으로 주소를 교체, 서버 재시작 직후에는 저장된 주소 사용

## ADR 0014 · 관리자 수동 CCTV 주소 갱신

- 상태: 채택, ADR 0013의 자동 갱신과 ADR 0010의 24시간 재호출 제한 대체
- 배경: 영상 주소 유효 여부는 목록 JSON에서 확인할 수 없고 정기 갱신으로도 재생 실패 시점을 보장할 수 없음
- 선택: 서버 시작·주기 작업·재생 실패는 ITS 목록을 호출하지 않고 관리자 버튼에서만 로그인 후 갱신
- 선택: 관리자 JWT 검증과 진행 중 요청 중복 방지 유지, 완료 후 재호출 대기 시간 없음
- 대안: 24시간 자동 갱신, 재생 오류에 따른 자동 재조회, 수동 요청에 24시간 대기 시간 적용
- 결과: 관리자가 영상 문제를 확인하고 즉시 새 주소를 요청할 수 있으나 화면을 확인하지 않으면 오래된 주소가 남을 수 있음

## ADR 0015 · 공식 ITS HLS 유형 사용

- 상태: 채택, ADR 0010의 HTTPS 주소 제한 대체
- 배경: 국토교통부 기술기준은 `cctvType=1`을 HLS로 정의, 기존 `4`는 공식 의미를 확인하지 못함
- 선택: `cctvType=1`을 요청하고 `cctvformat=HLS`·HTTP 또는 HTTPS 주소만 저장
- 대안: 동작을 확인한 문서 미기재 유형 `4` 유지, 서버에서 HTTP 영상을 HTTPS로 중계
- 결과: 2026-10-29 운영 응답의 HTTP HLS 재생목록·하위 재생목록·영상 조각·CORS 확인, HTTPS 화면 배포 시 영상 전달 경로 추가 필요

## ADR 0016 · 관제 화면의 다중 CCTV 상시 재생

- 상태: 채택, 선택 타일 확대는 ADR 0019로 대체
- 배경: CCTV 선택 후 HLS 연결을 시작해 첫 화면까지 검은 화면이 표시됨
- 선택: 관제 화면이 열리면 저장된 최대 6개 HLS 영상을 동시에 재생하고 선택한 타일을 같은 플레이어로 확대
- 선택: 첫 프레임 전 연결 상태 표시, 관제 화면 종료 시 영상 연결 해제, 영상 주소가 없는 CCTV는 안내 타일 표시
- 대안: 선택 후 재생 시작, 최근 프레임 미리보기 후 재생, Backend 영상 중계
- 결과: 선택 시 재연결 대기가 줄고 확대는 같은 플레이어 노드를 재사용
- 결과: 브라우저·네트워크 부하는 실제 관제 PC에서 검증 필요, 영상 서버 반복 접속 시 거절 가능

## ADR 0017 · 카메라별 화재 알림 번호와 SMS 발송

- 상태: 채택, ADR 0001의 "수신자 시스템 공용 목록"과 ADR 0008의 "`fire`·`smoke` 별도 알림" 대체
- 배경: 발표 데모에서 CCTV마다 담당 번호로 화재 문자를 보내고 발송 결과를 화면에서 확인해야 함
- 선택: 카메라당 번호 1개를 `cameras.alert_phone`에 저장하고 관리자 화면에서 설정
- 선택: `fire` 이벤트가 새로 생길 때만 발송, `smoke`는 화면 표시만
- 선택: 발송 결과를 `sms_logs`에 `sent`·`failed`·`skipped`로 기록, 발송 실패는 탐지 저장에 영향 없음
- 선택: 제공자는 `SMS_PROVIDER`로 교체, 기본 `console`, 데모 실발송은 솔라피 REST API
- 대안: 공용 수신자 목록 유지, 카메라-수신자 N:M 테이블, 알리고·NHN Cloud·네이버 클라우드 SENS, 안드로이드 폰 발송 장치(textbee)
- 결과: 번호 관리와 발송 지점이 단순하나 카메라당 번호는 1개로 제한
- 결과: textbee는 폰 전원·네트워크·앱 설치에 의존해 데모의 단순성에 맞지 않아 제외
- 결과: 솔라피는 가입 시 300P 무료, 본인인증 번호가 발신번호로 자동 등록되어 서류·폰·앱 없이 데모 가능
- 결과: 운영 전환이나 다른 발신번호 사용 시 서류 인증이 필요하고 제공자 재검토
- 결과: 2026-11-03 실발송 확인(SMS 18P, 단말 도착), 문구는 90바이트 이내로 제한, 초과 시 LMS 전환은 미확인
- 결과: 중복 방지는 실행(run) 단위, Test는 실행마다 1회, 실시간은 작업자 재시작 전까지 1회
- 결과: 공용 `sms_recipients`는 사용하지 않으며 기존 DB의 테이블은 삭제하지 않음

## ADR 0018 · 카메라별 보정값을 AI 설정 파일에 저장

- 상태: 채택
- 배경: 가창오리 실영상 검증에서 PTZ 라벨이 진북 기준이 아니고(라벨 + 약 120°) 화각이 코드 기본값 60°가 아닌 약 46~52°로 확인됨, 화각이 틀리면 자세 보정 게이트를 통과하는 체계적 오차가 남음(#56)
- 배경: 데모 Test 카메라는 해상도·화각이 서로 다른 고정 카메라이고, 밤에는 능선이 보이지 않아 낮에 구한 자세를 저장해 재사용해야 함
- 선택: 설치 정보(위경도)는 기존 DB `cameras` 값을 사용하고, 보정 결과(화각, 눈높이, Pan 오프셋, 프리셋 자세, 고정 카메라 자세)는 `ai/config/cameras.json`에 카메라 이름·ID 기준으로 저장
- 선택: 호출자가 메타데이터로 명시한 값이 설정 파일보다 우선, 설정 파일 값은 코드 기본값보다 우선
- 선택: 보정값마다 출처와 불확실성을 함께 기록, 보정 설정이 없는 카메라는 결과에 미보정으로 표시
- 대안: 보정값과 위경도를 모두 AI 설정 파일에 저장(DB 좌표와 중복·불일치 위험), 보정값을 DB 컬럼으로 추가하고 Backend가 AI 실행 인자로 전달(SQL·API·Backend 변경과 교차 리뷰 필요)
- 결과: Backend·DB 변경 없이 AI 담당 범위에서 보정값을 관리하고, 오프라인 보정 도구(#58)가 같은 파일을 생성
- 결과: AI 프로세스가 위경도를 받으려면 Backend가 카메라 좌표를 실행 인자로 넘기거나 AI가 조회해야 함, YOLO 연동(#60)에서 결정
- 결과: 카메라 식별 기준(DB 이름·ID)과 설정 파일 키를 일치시켜야 함, 보정값을 DB로 옮길 필요가 생기면 새 ADR로 대체

## ADR 0019 · 실시간 CCTV 선택 영상을 우측 패널에 표시

- 상태: 채택, ADR 0016의 "선택한 타일을 같은 플레이어로 확대" 대체
- 배경: 영상 월이 지도 아래에 있어 선택한 CCTV를 보려면 스크롤해야 하고, Test 카메라는 우측 상세 패널에 영상이 표시되어 방식이 달랐음
- 선택: 실시간 CCTV를 선택하면 Test 카메라처럼 지도 오른쪽 상세 패널에 영상을 표시
- 선택: 영상 월의 타일은 확대하지 않고 선택 강조와 해제만 제공
- 대안: 타일 확대 유지, 선택 시 영상 월로 자동 스크롤, 우측 패널이 같은 주소로 별도 연결(영상 서버가 두 번째 연결을 거절하는 것으로 추정)
- 결과: 선택한 영상 위치가 Test 카메라와 같아지고 선택 때 레이아웃이 움직이지 않음
- 결과: 우측 패널은 영상 월 타일의 영상을 `captureStream`으로 공유해 영상 서버에 두 번째 연결을 열지 않음
- 결과: 영상 월이 없는 화면(`/events/:id`)과 공유가 거절되는 브라우저는 직접 연결로 대체
- 결과: 공유하려면 hls.js(MSE) 재생이 필요해 브라우저 기본 HLS보다 hls.js를 우선 사용, ITS 영상 서버의 CORS 허용이 전제이며 현재 주소로는 미확인
- 결과: 영상 월에서 선택하면 우측 패널이 화면 밖일 수 있음

## ADR 0020 · ITS CCTV 식별 키에서 좌표 제외와 기존 행 재사용

- 상태: 채택
- 배경: 갱신할 때마다 ITS가 같은 CCTV의 좌표를 다른 자릿수로 반환(38.54174 → 38.5417)해 좌표가 들어간 식별 키가 바뀌었고, 같은 CCTV가 새 행으로 쌓여 6곳이 12행이 됨
- 선택: 식별 키를 도로구간 ID와 이름으로 생성하고 좌표는 제외
- 선택: 갱신 시 같은 키의 행을 찾고, 없으면 이름이 같고 좌표가 약 1km 안인 실시간 행의 키와 좌표를 갱신, 그래도 없을 때만 새 행 추가
- 대안: 좌표를 소수 둘째 자리로 반올림해 키에 포함, 이름만으로 매칭, 갱신 때마다 실시간 행을 모두 삭제 후 재등록
- 결과: 갱신해도 행이 늘지 않고 옛 방식 키로 저장된 행도 첫 갱신에서 이어받음, 카메라 ID가 유지되어 번호 설정과 탐지 기록이 끊기지 않음
- 결과: 같은 도로구간·이름의 서로 다른 CCTV는 같은 키가 되어 한 곳만 선택, 실제로 드문지는 미확인
- 결과: 이미 쌓인 중복 행은 자동으로 합치지 않으므로 별도 정리 필요

## ADR 0021 · 화재 이벤트 확인 상태를 DB에 저장

- 상태: 채택
- 배경: 화재 카메라를 빨갛게 표시하려면 "아직 처리되지 않은 화재"를 구분해야 하나, 이벤트에는 확인 여부가 없고 탐지 시작 시각만 있음
- 선택: `detection_events.acknowledged_at`에 운영자가 확인한 시각을 저장하고 관리자 API `POST /api/admin/events/:id/acknowledge`로 기록
- 선택: 확인하지 않은 `fire` 이벤트가 있는 카메라는 빨간색, 확인하면 파란색으로 복귀
- 대안: 최근 N분 이내 탐지를 빨간색으로 표시(시간 기준), 이벤트 종료 시각 기준 해제, 브라우저에만 확인 상태 저장
- 결과: 운영자가 확인하기 전에는 알람이 사라지지 않고 새로고침이나 다른 PC에서도 확인 상태가 유지됨
- 결과: 확인은 관리자 로그인이 필요하며 한 번 확인한 이벤트는 되돌리는 기능이 없음
- 결과: 같은 실행의 탐지는 이벤트 하나로 갱신되므로 확인 후 같은 실행에서 계속 탐지되어도 다시 빨개지지 않고, 새 실행의 탐지는 새 이벤트로 다시 알림
- 결과: 기존 DB의 쌓인 `fire` 이벤트는 모두 확인 대기로 시작

## ADR 0022 · 문자는 파랑에서 빨강으로 바뀔 때만 발송

- 상태: 채택, ADR 0008의 "같은 `run_id`와 클래스 조합에 한 번"과 ADR 0017의 "중복 방지는 실행(run) 단위" 대체
- 배경: 실행 단위 중복 방지는 서버 메모리에만 있어 작업자나 서버가 재시작되면 같은 불에 문자가 다시 가고 비용이 늘며, 반대로 끝나지 않는 실시간 실행은 몇 시간 뒤의 새 화재도 같은 이벤트로 취급해 놓침
- 선택: "알림 중"을 확인하지 않았고 마지막 탐지가 30분 안인 `fire` 이벤트로 정의하고, 같은 카메라에 알림 중인 이벤트가 없을 때 새 `fire` 이벤트가 생기면 문자 발송
- 선택: 마지막 탐지 후 30분이 지나면 확인하지 않아도 알림이 끝나 파란색으로 돌아가고, 이후 탐지는 새 이벤트
- 선택: 알림 중 여부는 Backend가 DB 시각으로 계산해 `is_alerting`으로 내려주고 마지막 탐지 시각은 `ended_at` 또는 `updated_at`을 사용, 확인 API는 `updated_at`을 바꾸지 않음
- 대안: 카메라별 마지막 발송 후 N분 간격 제한, 실행 단위 유지
- 결과: 재시작해도 DB 상태로 판단해 중복 발송하지 않고 같은 카메라의 새 화재는 놓치지 않음
- 선택: 알림 중에 작업자·서버가 재시작되어 같은 카메라에 이벤트가 하나 더 생겨도 한 번의 확인으로 함께 처리하고, 화면 알림 배너도 이미 알림 중인 카메라의 재시작 이벤트는 다시 띄우지 않음
- 결과: Test를 같은 카메라에서 알림 중에 다시 실행하면 문자가 가지 않음, 다시 보내려면 확인을 누르거나 30분을 기다려야 함
- 결과: 30분 기준은 `backend/src/services/fire-state.js`의 상수이며 설정 파일로 바꿀 수 없음, 빨간색이 꺼지는 시점은 화면 갱신 주기(30초)만큼 늦을 수 있음

## ADR 0023 · Test 탐지에 시간·영역별 투표 적용

- 상태: 채택, 5fps·16/20·IoU 0.2는 초기 검증 설정이며 최적값으로 검증되지 않음
- 배경: 고정 6프레임 간격은 원본 FPS에 따라 관찰 시간이 다르고 단일 프레임 오탐도 즉시 이벤트를 생성
- 선택: 영상 시각 기준 5fps로 분석하고 불 confidence 0.3·연기 0.5 기준 적용, 클래스별 같은 영역의 최근 20프레임 중 16회 이상 탐지 시 JSON 전송
- 선택: 박스 IoU 0.2 이상으로 일대일 연결하고 프레임당 한 표만 집계, 첫 20프레임이 채워진 뒤부터 판정하며 현재 탐지가 있는 영역만 전송
- 선택: 분석 프레임 사이 0.4초 초과 공백·시각 역행·큰 장면 전환에 투표 초기화, 큰 장면 전환 후 기존 자세 기반 위치 추정은 해당 실행에서 중단
- 대안: 한 프레임 즉시 전송, 20프레임 전부 연속 요구, 별도 시계열 검증 모델 학습
- 결과: 일시적인 미탐을 최대 4프레임 허용하고 약 4초 관찰 후 판정, 실제 지연에는 디코딩·모델 추론·통신·화면 조회 시간이 추가
- 결과: 모델 재학습과 API·DB 변경 없이 Test 실행에 적용, 실시간 작업자는 별도 구현 필요
- 결과: 지속적인 구름·안개 오탐과 점진적 PTZ 이동은 별도 대응 필요, 정상 영상의 시간당 오경보·산불 사건별 탐지율·탐지 지연·처리 부하로 설정 비교 필요

## ADR 0024 · 실시간 HLS 작업자와 공유 모델 연결

- 상태: 채택, 사용자 요청으로 테스트 실행 생략
- 배경: 실시간 CCTV는 화면 재생과 Backend 실행 계약만 있고 실제 AI 작업자가 없음
- 선택: 기본 작업자에서 카메라별 HLS 디코딩·영상 시각 기준 5fps 수신, 공유 YOLO로 묶어 추론하고 ADR 0023 판정을 재사용
- 선택: 최대 3프레임 대기열과 수신 후 1초 유효시간 적용, 누락·재접속·장면 전환에 판정 초기화, HTTP 전송은 별도 스레드에서 최신 결과만 유지
- 선택: 위치 추정은 이름이 일치하는 고정 자세 보정값이 있는 카메라에 한정, 나머지는 null
- 대안: 카메라마다 모델 복제, 모든 프레임을 무제한 적재, 별도 영상 파일 저장 후 분석
- 결과: Backend 재시작 시 저장된 6대 자동 분석, 장비가 5fps를 감당하지 못하면 프레임 폐기와 판정 초기화가 늘어나므로 실제 처리 성능 확인 필요
- 결과: 이벤트 단위 확인(ADR 0021)과 함께 쓰며 ADR 0021의 "확인하기 전에는 알람이 사라지지 않음"은 30분 후 자동 종료로 바뀜

## ADR 0025 · 실시간 탐지 선전송과 비동기 위치 보완

- 상태: 채택, ADR 0024의 위치 계산 흐름·콜백 유효시간 구체화
- 배경: 최초 DEM 준비와 위치 계산을 공유 추론 루프에서 수행하면 다른 카메라의 탐지까지 대기, 위치 계산 후 전송 시각을 새로 기록하면 오래된 표본이 최신 결과로 취급됨
- 선택: 16/20 확정 탐지를 위치 없이 먼저 전송하고 Backend 수락 뒤 별도 위치 작업자가 같은 실행·클래스의 이벤트에 위치 보완, 기존 JSON·이벤트 집계·문자 중복 방지 계약 재사용
- 선택: 첫 분석 프레임부터 고정 자세 카메라의 DEM을 백그라운드에서 준비, 카메라별 준비 1개·카메라와 클래스별 최신 위치 표본 1개만 대기, 확정 탐지의 위치 보완 우선
- 선택: 추론 전·후 프레임 유효시간은 로컬 대기열 등록 후 1초, 최초 탐지·위치 보완 콜백은 같은 등록 시각부터 5초, 재접속·누락·장면 전환 전의 대기 표본 무효화
- 선택: 표준 입력은 UTF-8로 읽고 디코더 시각 누락·반복은 마지막 영상 시각과 FPS로 복원, 실제 양수 시각 역행은 재접속 처리
- 선택: 배치 추론·프레임 대기·DEM 준비·위치 계산·전송 시간을 단계별 집계해 30초마다 로그 기록
- 대안: 모든 카메라가 위치 계산 완료까지 대기, 위치 없이 탐지만 제공, 카메라마다 위치 작업자와 DEM 복제
- 결과: 최초 화재 알림은 위치 계산을 기다리지 않으며 위치 보완은 새 이벤트나 추가 문자를 만들지 않음, 위치 작업자 한 개의 지연은 다른 카메라의 위치 보완에는 영향을 줄 수 있음
- 결과: 5초 넘게 지연된 위치는 폐기하고 준비된 DEM으로 후속 최신 표본 계산, 이미 전송 중인 HTTP 요청 취소와 원본 촬영 시각부터의 HLS 전체 지연 산출은 미지원
- 결과: 단위·모의 지연·API 회귀 테스트로 순서와 무효화 검증, 실제 관제 장비의 6대 동시 5fps 처리 속도·위치 지연은 별도 측정 필요

## ADR 0026 · 자세 메타데이터 없는 실시간 카메라의 자동 위치 추정

- 상태: 채택, ADR 0024의 고정 자세 전용 제한과 ADR 0025의 위치 준비·복구 정책 대체
- 배경: 능선·DEM 기반 자동 자세 추정이 구현되어 있으나 실시간 작업자가 `fixed_pose` 없는 카메라를 세션 생성 전에 제외해 현재 실시간 6대의 위치 추정 미실행
- 선택: 위경도가 있으면 기존 `LocationSession` 생성, 처음에는 등록 고정 자세 우선·없으면 360° 능선 정합으로 Pan·Tilt·Roll 추정, 품질 게이트를 통과한 경우에만 화점 좌표 산출
- 선택: 사용자가 선택한 기존 알고리즘의 기본 화각 60° 가정 유지, 미등록 화각 경고와 54°·66° 대체 자세의 오차 범위 평가 유지, 실제 화각을 확보한 카메라만 제공하는 제한은 적용하지 않음
- 선택: 위치 작업자는 비동기 유지, DEM·능선·정합 준비 실패를 30초부터 최대 300초 간격으로 재시도하고 좌표 없는 카메라는 생략
- 선택: 큰 장면 변화·해상도 변경·재접속 시 자세와 이전 대기 결과 무효화, 연속 10프레임·1.8초 이상 안정 후 고정 자세를 재사용하지 않고 자동 재추정
- 선택: 탐지 투표와 자세의 유효기간을 분리해 단순 프레임 누락에는 투표·이전 표본만 초기화, 같은 촬영 방향에서 완료된 자세 준비는 재사용
- 대안: 고정 자세 카메라로 제한 유지, 실제 화각 확인 전까지 좌표 생략, 프레임마다 전체 자세 재추정
- 결과: 현재 실시간 카메라도 자동 위치 추정을 시도하며 실패 시 위치 없이 탐지·알림 계속, 준비 상태·실패 사유·재시도 간격·기본 화각 가정을 로그로 확인 가능
- 결과: 기본 화각 가정의 위치 오차와 실제 6대 동시 처리 성능은 별도 검증 필요, 작은 PTZ·줌 변화의 완전한 감지와 이전 이벤트 좌표 삭제는 이번 범위에서 제외
