# FireGuard AI 아키텍처 결정 기록

[시스템 아키텍처](System_architecture.md) · [API 명세](API_SPEC.md) · [ERD](DATABASE.md)

## ADR 0001 · 관리자와 SMS 수신자

- 상태: 채택
- 관리자 계정은 `admins`에 저장하고 로그인은 JWT 사용
- 수신자는 관리자별이 아닌 시스템 공용 목록으로 관리
- 비밀번호는 해시로 저장하고 SMS 인증 정보는 Backend에서 관리

## ADR 0002 · 녹화 영상 저장

- 상태: 현행
- 원본 영상은 `data/videos/`에 저장하고 DB에는 경로와 메타데이터 저장
- Backend가 등록 영상을 HTTP Range 방식으로 제공

## ADR 0003 · 영상 4개 일괄 분석

- 상태: ADR 0004로 대체
- 이전 결정: Test 버튼 하나로 녹화 영상 4개를 동시에 분석

## ADR 0004 · 카메라별 테스트와 실시간 구분

- 상태: 현행
- `cameras.source_type` 값은 `test` 또는 `live`
- `test` 카메라별 버튼은 연결된 영상 하나를 분석
- `live` 카메라는 ITS CCTV 영상 주소 사용

## ADR 0005 · Python 표준 출력으로 영상 전달

- 상태: ADR 0006으로 대체
- 이전 결정: Python 표준 출력의 MJPEG 프레임을 Backend가 프론트에 전달

## ADR 0006 · AI 영상·탐지 결과 전송

- 상태: 현행
- AI는 MJPEG 영상을 `POST /api/test-runs/:id/video`로 전송
- AI는 탐지 JSON을 `POST /api/detections`로 전송
- Backend는 영상을 저장하지 않고 `GET /api/test-runs/:id/stream`으로 중계
- 실행 ID로 영상과 탐지 결과를 연결
- Backend가 실행 ID를 생성해 `run_id`, `camera_id`, 영상 경로와 전송 주소를 AI 프로세스 인자로 전달

## ADR 0007 · Test API 인증

- 상태: 채택
- Frontend가 호출하는 Test 실행·상태·영상 스트림 API는 관리자 JWT로 인증
- AI가 호출하는 영상·탐지 콜백 API는 `AI_CALLBACK_TOKEN`으로 인증

## ADR 0008 · Test 실행 중 SMS 중복 방지

- 상태: 제안
- 데모에서는 같은 `run_id`와 탐지 클래스 조합에 SMS를 한 번만 발송
- `fire`와 `smoke`는 각각 별도 알림
- 실시간 CCTV의 연속 탐지 이벤트 구분과 재알림 간격은 실제 탐지 누락·오탐을 확인한 뒤 결정

## ADR 0009 · Test 실행 상태 관리

- 상태: 채택
- 실행 상태와 영상 중계 연결은 Backend 프로세스 메모리에서 관리
- 탐지 이벤트는 `detection_events`에 저장하고 같은 실행·클래스의 후속 탐지는 기존 이벤트를 갱신
- Backend 재시작 시 진행 중 실행과 스트림은 종료되며 상태 조회는 유지되지 않음

## ADR 0010 · ITS CCTV 목록 수동 갱신

- 상태: 수동 갱신은 채택, 예시 모드는 ADR 0011로 대체, 24시간 재호출 제한은 ADR 0014로 대체, HTTPS 주소 제한은 ADR 0015로 대체
- 배경: ITS 월 호출 한도 1000건, 지도 방문마다 제공자 API 조회 시 발표 전 한도 소진 가능
- 선택: Backend 관리자 API에서만 ITS 목록 요청, 최대 6개 HTTPS HLS CCTV를 지역 분산 선택해 로컬 파일에 저장
- 선택: 성공·실패 모두 호출 시도를 기록하고 24시간 재호출 차단, 지도 조회는 캐시만 읽음
- 선택: ITS 응답 후 DB 저장 실패 시 대기 목록을 남기고 제공자 재호출 없이 저장 재개
- 선택: 키 없는 fixture 모드는 예시 좌표만 제공하며 실제 영상으로 표시하지 않음
- 대안: 매 화면 조회 시 ITS 요청, 자동 주기 갱신, 브라우저에 ITS 키 전달
- 결과: 정상 갱신 시 월 최대 약 31회 호출, 장애 시 오래된 목록 유지, 실키 테스트에서 HLS·CORS 확인

## ADR 0011 · ITS 예시 모드 제거

- 상태: 채택, ADR 0010의 fixture 모드 선택을 대체
- 배경: 실제 ITS 조회·HLS 재생목록·AI MJPEG 프레임 전달을 확인
- 선택: 예시 CCTV 목록과 모드 분기를 제거하고 저장된 실제 목록만 반환
- 대안: 예시 모드를 개발 전용으로 유지
- 결과: 키 없이도 저장된 목록을 조회할 수 있지만 최초 목록은 비어 있음

## ADR 0012 · 6개 CCTV 감시 작업자 관리

- 상태: 채택
- 배경: 서버가 켜진 동안 6개 영상을 계속 분석해야 하고 AI 담당자의 실시간 코드가 아직 미완성
- 선택: Backend가 저장된 6개 CCTV와 실행 ID를 AI 작업자 한 개에 표준 입력 JSON으로 전달
- 선택: 카메라별 프레임 상태 신호를 수신하고 작업자 종료·120초 신호 누락 시 재시작
- 선택: AI 파일이 설정되지 않으면 대기 상태를 공개하고 ITS 목록 API는 자동 호출하지 않음
- 대안: 카메라마다 YOLO 프로세스 한 개, 수동 60초 실행
- 결과: AI 모델을 한 번 로드할 수 있고 Backend만으로 실행 관리 검증 가능, 실제 분석은 AI 작업자 연결 후 검증

## ADR 0013 · ITS CCTV 주소 정기 갱신

- 상태: ADR 0014로 대체, ADR 0011의 자동 갱신 없음 선택 대체
- 배경: 실시간 영상 주소가 만료될 수 있고 서버를 계속 실행해야 함, 월 호출 한도는 1000건
- 선택: 서버 시작과 화면 조회는 ITS를 호출하지 않고 서버 실행 후 24시간마다 목록 갱신 시도
- 선택: 호출 시도 기록으로 최소 24시간 간격 유지, 성공 시 감시 작업자에 새 주소 전달
- 대안: 화면 조회 때마다 호출, 수동 갱신만 사용
- 결과: 장시간 실행 시 약 30회/월 요청으로 주소를 교체, 서버 재시작 직후에는 저장된 주소 사용

## ADR 0014 · 관리자 수동 CCTV 주소 갱신

- 상태: 채택, ADR 0013의 자동 갱신과 ADR 0010의 24시간 재호출 제한 대체
- 배경: 영상 주소 유효 여부는 목록 JSON에서 확인할 수 없고 정기 갱신으로도 재생 실패 시점을 보장할 수 없음
- 선택: 서버 시작·주기 작업·재생 실패는 ITS 목록을 호출하지 않고 관리자 버튼에서만 로그인 후 갱신
- 선택: 관리자 JWT 검증과 진행 중 요청 중복 방지 유지, 완료 후 재호출 대기 시간 없음
- 대안: 24시간 자동 갱신, 재생 오류에 따른 자동 재조회, 수동 요청에 24시간 대기 시간 적용
- 결과: 관리자가 영상 문제를 확인하고 즉시 새 주소를 요청할 수 있으나 화면을 확인하지 않으면 오래된 주소가 남을 수 있음

## ADR 0015 · 공식 ITS HLS 유형 사용

- 상태: 채택, ADR 0010의 HTTPS 주소 제한 대체
- 배경: 국토교통부 기술기준은 `cctvType=1`을 HLS로 정의, 기존 `4`는 공식 의미를 확인하지 못함
- 선택: `cctvType=1`을 요청하고 `cctvformat=HLS`·HTTP 또는 HTTPS 주소만 저장
- 대안: 동작을 확인한 문서 미기재 유형 `4` 유지, 서버에서 HTTP 영상을 HTTPS로 중계
- 결과: 2026-10-29 운영 응답의 HTTP HLS 재생목록·하위 재생목록·영상 조각·CORS 확인, HTTPS 화면 배포 시 영상 전달 경로 추가 필요
